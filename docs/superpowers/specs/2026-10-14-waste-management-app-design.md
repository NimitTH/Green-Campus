# Design Spec: เว็บแอปกิจกรรมอนุรักษ์สิ่งแวดล้อมและแลกแต้มรักโลก (Green Campus)

- **วันที่:** 14 ตุลาคม 2026
- **สถานะ:** ผู้ใช้อนุมัติครบแล้ว (14 ต.ค. 2026) ยังไม่เริ่มเขียนโค้ด ขั้นถัดไปคือแผนพัฒนาตามเฟส
- **เส้นทางกระบวนการ:** Architectural (โปรเจกต์ใหม่) → spec นี้ → ขั้นเขียนแผนพัฒนา (writing-plans)
- **ผู้ใช้เอกสาร:** นักเรียนเจ้าของโปรเจกต์ (ทำคนเดียว)

---

## 1. เป้าหมายและบริบท

### 1.1 เป้าหมาย
เว็บแอปที่ให้ครู/admin สร้างกิจกรรมอนุรักษ์สิ่งแวดล้อม (เก็บขยะ ปลูกต้นไม้ ฯลฯ) นักเรียนเข้าร่วมและส่งผลพร้อมหลักฐาน ครู/admin ตรวจ ระบบให้แต้มและคำนวณ carbon footprint ที่ลดได้ แต้มแลกของรางวัลรักโลกได้ผ่านเว็บ และรับของที่แผนก

### 1.2 บริบทการใช้งาน (ตามที่ผู้ใช้ระบุ)
- เป็น **โปรเจกต์ส่งอาจารย์** ต้องสาธิตหน้าห้องให้ครู เพื่อนในห้อง รุ่นน้อง รุ่นพี่ลองใช้เอง ส่วนใหญ่เข้าจากมือถือโดยสแกน QR
- **กำหนดส่ง:** ต้นเดือนมีนาคม 2027 (เหลือเวลาราว 4 เดือนครึ่งนับจากวันที่เขียน spec)
- **Stack:** Next.js + Supabase, deploy บน Vercel + Supabase Cloud (แพ็กเกจฟรี)

### 1.3 เกณฑ์ความสำเร็จ
1. ในวันสาธิต ผู้ชมสมัครด้วยมือถือตัวเองแล้วทำ flow ครบ: เข้าร่วมกิจกรรม → ส่งผล → ครูอนุมัติ → เห็นแจ้งเตือน → แลกของ → ดาวน์โหลดใบเสร็จ
2. แต้มไม่ติดลบและสต็อกไม่เกิน แม้มีการกดพร้อมกัน
3. นักเรียนทำให้ตัวเองได้แต้มเกินจริงหรือยกระดับสิทธิ์ตัวเองไม่ได้
4. ลืมรหัสผ่านใช้งานได้จริงด้วยอีเมลจริง
5. dashboard อันดับ และรายงานมีข้อมูลให้ดูตั้งแต่เปิดหน้า (ข้อมูลตัวอย่าง)

---

## 2. ขอบเขต

### 2.1 อยู่ในขอบเขต
สมัคร/เข้าสู่ระบบ/ลืมรหัสผ่าน, แก้ profile, กิจกรรม (3 ชนิด), เข้าร่วม, จุดชั่งและรหัสยืนยัน, ส่งผลพร้อมรูป, ตรวจอนุมัติ/ปฏิเสธ, ledger แต้มและ carbon, ของรางวัล, cart, ออเดอร์, ใบเสร็จ PDF, ยืนยันรับของ, ออเดอร์หมดอายุ 7 วัน, แจ้งเตือนในเว็บ (Realtime), อันดับ (รายเดือน/ตลอดกาล), dashboard (นักเรียน / เว็บรวม / ครู-admin), รายงาน CSV และ PDF พร้อมกราฟ, บทความความรู้, จัดการผู้ใช้และอัตราคะแนน (admin), ข้อมูลตัวอย่างและบัญชีสาธิต

### 2.2 นอกขอบเขต (ไม่ทำใน spec นี้)
- แจ้งเตือนทางอีเมลหรือ LINE (อีเมลใช้เฉพาะสมัครและลืมรหัสผ่าน)
- อันดับรายห้อง/รายชั้นปี และฟิลด์ห้อง/ชั้นปีใน profile
- การแปลง carbon เป็นสิ่งที่เห็นภาพ (เช่น เท่ากับต้นไม้กี่ต้น)
- โหมด C ให้เจ้าหน้าที่จุดชั่งกรอกน้ำหนักเทียบกับนักเรียน
- ตรวจรูปซ้ำด้วยแฮช (เป็น **ฟีเจอร์เสริม** ดูหัวข้อ 12)
- หลายภาษา (ไทยอย่างเดียว), แอปมือถือเนทีฟ, ใช้งานออฟไลน์, ระบบชำระเงินจริง
- นักเรียนยกเลิกออเดอร์เอง (ยกเลิกได้เฉพาะครู/admin หรือหมดอายุอัตโนมัติ)

## 3. บันทึกการตัดสินใจ

| หัวข้อ | การตัดสินใจ |
|---|---|
| ชนิดกิจกรรม | flow เดียวกันทุกชนิด เปลี่ยนแค่หน่วยวัด: `waste` (กรัมแยก 4 กลุ่ม), `trees` (จำนวนต้น), `fixed` (แต้มคงที่ต่อการเข้าร่วม) |
| การยืนยันผล | นักเรียนกรอกน้ำหนักเอง + รูปที่เห็นตัวเลขเครื่องชั่ง + **รหัสยืนยัน 6 หลักใช้ครั้งเดียว** จากเจ้าหน้าที่จุดชั่ง (หมดอายุ 30 นาที) + ครู/admin ตรวจอีกชั้น |
| บังคับรหัส | ตั้งต่อกิจกรรม (`requires_code`) ค่าเริ่มต้น: บังคับสำหรับ `waste`, ไม่บังคับสำหรับ `trees`/`fixed` ครูเปิดบังคับเพิ่มได้ |
| ประเภทขยะ | 4 กลุ่ม: พลาสติก, กระดาษ, โลหะ/แก้ว, ขยะทั่วไป/อื่นๆ แต่ละกลุ่มมีแต้มและ carbon ต่อ kg ที่ admin ปรับได้ |
| บทบาท | ทุกคนสมัครเป็น `student` เสมอ admin ยกระดับเป็น `teacher`/`admin` ผ่านหน้าเว็บ admin คนแรกตั้งผ่านฐานข้อมูล |
| ออเดอร์ | หักแต้มและตัดสต็อกทันทีที่แลก ไม่รับภายใน 7 วันยกเลิกอัตโนมัติและคืนแต้ม/สต็อก |
| แจ้งเตือน | ในเว็บอย่างเดียว (กระดิ่ง + Realtime + หน้าประวัติ) |
| อันดับ | ตาม carbon ที่ลดได้ แสดง `display_name` (ค่าเริ่มต้น = ชื่อจริง นักเรียนเปลี่ยนเป็นชื่อเล่นได้) รายเดือนและตลอดกาล |
| ที่ deploy | Vercel + Supabase Cloud (ฟรี) ออกแบบให้ย้ายไปรัน local ได้ |
| ข้อมูลสาธิต | seed ข้อมูลตัวอย่าง + บัญชีสาธิต 3 บัญชี (นักเรียน ครู admin) |
| แนวทางสถาปัตยกรรม | ผสม: งานที่ต้องเป็นอะตอมิกเขียนเป็นฟังก์ชัน Postgres, งานทั่วไปใช้ Server Actions + RLS |
| อีเมล | custom SMTP ผ่านผู้ให้บริการอีเมลแพ็กเกจฟรี คงการยืนยันอีเมลไว้ (สลับเป็นปิดการยืนยันได้ถ้าวันสาธิตมีปัญหา) |
| รายงาน | CSV (UTF-8 มี BOM) และ PDF สรุปพร้อมกราฟ เลือกช่วงวันที่ได้ |
| สภาพแวดล้อมทดสอบ | ถ้ารัน Docker ไม่ได้ ใช้โปรเจกต์ Supabase ฟรีตัวที่สองเป็นโปรเจกต์ทดสอบ |

## 4. สถาปัตยกรรม

### 4.1 เทคโนโลยี
- **Frontend/Server:** Next.js (App Router, TypeScript), Tailwind CSS, Recharts สำหรับกราฟบนเว็บ
- **Backend:** Supabase — Auth, Postgres, Storage (รูปหลักฐาน), Realtime (แจ้งเตือน), pg_cron (ออเดอร์หมดอายุ)
- **Hosting:** Vercel (เว็บ), Supabase Cloud (ข้อมูล)
- **ฟอนต์:** Sarabun หรือ Noto Sans Thai สีหลักโทนเขียว

### 4.2 โมดูล (แต่ละโมดูลทำหน้าที่เดียว)
1. **Auth & Roles:** Supabase Auth + ตาราง `profiles` (trigger สร้างแถว role = `student` ตอนสมัคร)
2. **Activities:** กิจกรรม หน่วยวัด การเข้าร่วม
3. **Submissions & Codes:** ออกรหัสจุดชั่ง ส่งผล ตรวจ
4. **Ledger:** สมุดแต้มและ carbon (เพิ่มรายการอย่างเดียว)
5. **Rewards & Orders:** ของรางวัล cart ออเดอร์ สต็อก ใบเสร็จ
6. **Notifications:** ตารางแจ้งเตือน + Realtime
7. **Reporting:** ฟังก์ชันอันดับ dashboard และรายงาน

### 4.3 หลักการแบ่งหน้าที่
- **ฟังก์ชัน Postgres (`SECURITY DEFINER`)** สำหรับทุกการเปลี่ยนแปลงที่เกี่ยวกับแต้ม สต็อก รหัส และสถานะผล/ออเดอร์ (ทำงานเป็น transaction เดียว)
- **Server Actions + RLS** สำหรับ CRUD ทั่วไป (กิจกรรม ของรางวัล บทความ profile cart)
- **Route Handlers (ฝั่งเซิร์ฟเวอร์)** สำหรับใบเสร็จ PDF รายงาน CSV/PDF และงานล้างรูปค้าง
- ไคลเอนต์ในเบราว์เซอร์ใช้ anon key เท่านั้น `service_role` key อยู่ฝั่งเซิร์ฟเวอร์

### 4.4 สภาพแวดล้อม
- **production:** โปรเจกต์ Supabase ฟรีตัวที่ 1 + Vercel
- **ทดสอบ:** Supabase local ผ่าน Docker หรือโปรเจกต์ฟรีตัวที่ 2 (ใช้โควตา 2 โปรเจกต์ของแพ็กเกจฟรีจนครบ)
- Schema ทั้งหมดอยู่ในไฟล์ migration ใน repo เพื่อสร้างซ้ำได้ทุกสภาพแวดล้อม

## 5. โครงสร้างข้อมูล

**หลักคิด**
- ตารางหลักเก็บของจริง ยอดคงเหลือคำนวณจาก `ledger_entries` ไม่เก็บเป็นคอลัมน์ที่แก้ทับ
- น้ำหนักเก็บเป็น **กรัม** จำนวนเต็ม (ฟอร์มกรอก kg และขีด 1 ขีด = 100 กรัม ระบบแปลง)
- แต้มและ carbon ถูกคำนวณตอนอนุมัติและบันทึกลง ledger ทันที การแก้อัตราทีหลังไม่กระทบผลที่อนุมัติไปแล้ว
- ทุกตารางมี `id` (uuid), `created_at` (timestamptz) ส่วนตารางที่แก้ไขได้มี `updated_at` เวลาแสดงผลใช้เขตเวลา Asia/Bangkok
- กิจกรรมที่มีผลที่ส่งแล้วห้ามลบ ให้ปิด (`closed`) แทน

| ตาราง | ฟิลด์สำคัญ |
|---|---|
| `profiles` | role (`student`/`teacher`/`admin`), full_name, display_name, is_demo (boolean) |
| `waste_categories` | name, points_per_kg (จำนวนเต็ม), carbon_kg_per_kg (numeric), source_note (ที่มาของค่า) |
| `activities` | title, description, location, is_offsite, starts_at, ends_at, status (`draft`/`open`/`closed`), type (`waste`/`trees`/`fixed`), requires_code, unit_points, unit_carbon_kg (เว้นว่างได้), max_per_submission, created_by |
| `participations` | activity_id, student_id (unique คู่นี้) |
| `weigh_codes` | activity_id, student_id, code (6 หลัก), issued_by, expires_at (+30 นาที), used_at, revoked_at, attempts (เริ่มที่ 0) |
| `submissions` | activity_id, student_id, code_id (เว้นว่างได้ถ้าไม่บังคับรหัส), evidence_path, evidence_sha256 (เว้นว่างได้ ใช้กับฟีเจอร์เสริม), status (`pending`/`approved`/`rejected`), reviewed_by, reviewed_at, reject_reason |
| `submission_items` | submission_id, waste_category_id (เฉพาะ `waste`), quantity (กรัม หรือจำนวนต้น) |
| `ledger_entries` | student_id, kind (`earn`/`redeem`/`refund`/`adjust`), points, carbon_kg, ref_submission_id, ref_order_id, note (เหตุผลของ `adjust`), created_by |
| `rewards` | name, points_cost, stock, image_path, active |
| `cart_items` | student_id, reward_id, qty (unique คู่ student_id + reward_id) |
| `orders` | student_id, status (`pending_pickup`/`completed`/`cancelled`/`expired`), total_points, expires_at (+7 วัน), completed_by, completed_at |
| `order_items` | order_id, reward_id, qty, unit_cost (ราคา ณ ตอนสั่ง) |
| `notifications` | user_id, type, title, body, link, read_at |
| `articles` | title, slug, body, cover_path, published, author_id |

### 5.1 ข้อกำหนดของข้อมูล
- `ledger_entries.points` ใช้เครื่องหมายเป็นตัวกำหนดทิศทาง: `earn` เป็นบวก, `redeem` เป็นลบ, `refund` เป็นบวก, `adjust` บวกหรือลบ
- `carbon_kg` ของ `redeem` และ `refund` เป็น 0 เสมอ
- **แต้มคงเหลือ** = ผลรวม `points` ของนักเรียนทุก kind
- **carbon สะสม (ใช้กับอันดับและ dashboard)** = ผลรวม `carbon_kg` ของ kind `earn` และ `adjust`
- `weigh_codes`: มีได้ **หนึ่งรหัสที่ยังใช้ได้** ต่อคู่ (student, activity) (partial unique index บนแถวที่ `used_at` และ `revoked_at` ว่าง)
- `submission_items`: กิจกรรม `waste` ต้องมี `waste_category_id` และ quantity เป็นกรัม > 0, กิจกรรม `trees` มีหนึ่งแถว quantity = จำนวนต้น, กิจกรรม `fixed` มีหนึ่งแถว quantity = 1

## 6. กฎธุรกิจและสูตรคำนวณ

### 6.1 สูตรคำนวณ (คำนวณตอนอนุมัติ จากอัตรา ณ ขณะนั้น)
- **`waste`:** แต้ม = ปัดลง(ผลรวมของ [กรัม × `points_per_kg`] ของแต่ละกลุ่ม ÷ 1000) เป็นจำนวนเต็มต่อหนึ่งผลที่ส่ง, carbon (kg CO2e) = ผลรวมของ [กรัม × `carbon_kg_per_kg` ÷ 1000] เก็บทศนิยม 3 ตำแหน่ง
- **`trees`:** แต้ม = จำนวนต้น × `unit_points`, carbon = จำนวนต้น × `unit_carbon_kg` (ว่าง = 0)
- **`fixed`:** แต้ม = `unit_points`, carbon = `unit_carbon_kg` (ว่าง = 0)
- `max_per_submission` ใช้ตรวจตอนส่ง: `waste` = ผลรวมกรัมสูงสุดต่อการส่ง, `trees` = จำนวนต้นสูงสุด, `fixed` ไม่ใช้

### 6.2 ค่าอ้างอิง carbon
ห้ามเดาตัวเลข ค่า `carbon_kg_per_kg` ของ 4 กลุ่ม และค่าของต้นไม้ต้องมาจากแหล่งอ้างอิงที่ตรวจสอบได้ โดย **ผู้ใช้กำหนดให้ใช้ค่าขององค์การบริหารจัดการก๊าซเรือนกระจก (อบก. / TGO) เป็นแหล่งอ้างอิงหลัก** พร้อมบันทึกที่มาใน `source_note` ถ้า อบก. ไม่มีค่าที่ตรงกับบางกลุ่ม (เช่น ขยะทั่วไป/อื่นๆ หรือต้นไม้) หรือหาค่าที่เชื่อถือได้ไม่ครบ ต้องแจ้งเจ้าของโปรเจกต์ก่อนทำ seed และอาจกำหนดว่าค่านั้นเป็นค่าประมาณที่ระบุไว้ชัดเจนในหน้ารายงาน

### 6.3 การเข้าร่วมและช่วงเวลาส่งผล
- กดเข้าร่วมได้เมื่อกิจกรรม `open` และยังไม่ถึง `ends_at` (ผ่านฟังก์ชัน `join_activity`) กดซ้ำไม่ได้
- ส่งผลได้ตั้งแต่ `starts_at` จนถึง **3 วันหลัง `ends_at`** (เผื่อชั่งช้า)
- หนึ่งกิจกรรมส่งได้หลายครั้ง ถ้ากิจกรรมบังคับรหัส ทุกครั้งต้องมีรหัสใหม่

### 6.4 รหัสยืนยัน
- ออกรหัสได้เฉพาะกิจกรรมที่ `requires_code` = true, นักเรียนต้องเป็นผู้เข้าร่วม และอยู่ในช่วงเวลาส่งผล
- ออกรหัสใหม่ให้คู่เดิม จะ `revoked_at` รหัสเก่าที่ยังไม่ใช้ทันที
- รหัสสร้างด้วยตัวสุ่มที่ปลอดภัย (ไม่ใช้ `random()` ธรรมดา)
- ใส่รหัสผิดครบ **5 ครั้ง** รหัสถูกล็อก ต้องขอใหม่

### 6.5 การตรวจผล
- อนุมัติ/ปฏิเสธได้เฉพาะผลสถานะ `pending` และผู้ตรวจต้องเป็น staff ที่ **ไม่ใช่เจ้าของผล**
- ปฏิเสธต้องใส่เหตุผล ส่งใหม่ต้องขอรหัสใหม่ถ้ากิจกรรมบังคับรหัส
- ผลที่อนุมัติแล้วแก้ไม่ได้ ถ้าอนุมัติผิด admin ทำรายการ `adjust` (พร้อม `note`)

### 6.6 การแลกของ
- Cart ไม่กันสต็อก แค่จดไว้
- `checkout` สำเร็จหรือล้มเหลวทั้งออเดอร์ ถ้าแต้มหรือสต็อกไม่พอ ไม่มีอะไรเปลี่ยนและตอบกลับว่าชิ้นไหนติด
- ออเดอร์หมดอายุเมื่อพ้น 7 วันนับจากสร้าง

## 7. Flow หลักและฟังก์ชันฐานข้อมูล

ทุกฟังก์ชันตรวจ `auth.uid()` และบทบาทของผู้เรียกในตัวเอง ตั้ง `search_path` ตายตัว และทำงานใน transaction เดียว

| ฟังก์ชัน | ผู้เรียก | หน้าที่ |
|---|---|---|
| `join_activity(activity_id)` | student | ตรวจกิจกรรม `open` และยังไม่ถึง `ends_at` แล้วสร้างการเข้าร่วม |
| `issue_weigh_code(activity_id, student_id)` | staff | ตรวจเงื่อนไข 6.4, revoke รหัสเก่า, สร้างรหัสใหม่, คืนรหัสและเวลาหมดอายุ |
| `submit_result(activity_id, code, items, evidence_path)` | student | ดูรายละเอียดด้านล่าง |
| `approve_submission(submission_id)` | staff | ล็อกแถวผล ตรวจ `pending` และไม่ใช่เจ้าของ คำนวณตาม 6.1 บันทึก `earn` เปลี่ยนสถานะ แจ้งนักเรียน |
| `reject_submission(submission_id, reason)` | staff | ตรวจเงื่อนไข เปลี่ยนสถานะ แจ้งนักเรียน |
| `checkout()` | student | ล็อกโปรไฟล์ → คำนวณแต้มจาก ledger → ล็อกแถวของรางวัลตรวจสต็อก → ตัดสต็อก, สร้างออเดอร์ (บันทึก `unit_cost`), บันทึก `redeem`, ล้าง cart, แจ้งเตือน |
| `complete_order(order_id)` | staff | `pending_pickup` → `completed` แจ้งนักเรียน |
| `cancel_order(order_id)` | staff | `pending_pickup` → `cancelled` คืนสต็อกและบันทึก `refund` แจ้งนักเรียน |
| `expire_orders()` | pg_cron (ทุกชั่วโมง) และปุ่ม admin | ออเดอร์ที่พ้น `expires_at` → `expired` คืนสต็อกและ `refund` แจ้งนักเรียน |
| `set_user_role(user_id, role)` | admin | เปลี่ยนบทบาท (ดูกฎในหัวข้อ 8.3) |
| `adjust_ledger(student_id, points, carbon_kg, note)` | admin | เพิ่มรายการ `adjust` |
| `leaderboard(period)` | ผู้ล็อกอิน | ส่งคืน display_name กับ carbon สะสม รายเดือน (ปฏิทินเขตเวลา Asia/Bangkok) หรือตลอดกาล โดยไม่เปิดเผย ledger ของคนอื่น |
| `public_stats()` | ทุกคน (anon) | ส่งคืนยอดรวมของทั้งเว็บ (carbon, น้ำหนักขยะ, จำนวนต้นไม้) เท่านั้น ไม่มีข้อมูลรายบุคคล |

### 7.1 รายละเอียด `submit_result`
1. **ลำดับฝั่งไคลเอนต์:** อัปโหลดรูปก่อน แล้วค่อยเรียกฟังก์ชัน (กันรหัสถูกใช้ทิ้งเมื่ออัปโหลดล้มเหลว)
2. ฟังก์ชันตรวจ: เป็นผู้เข้าร่วม, อยู่ในช่วงเวลาส่ง, ไม่เกิน `max_per_submission`, ปริมาณเป็นบวก, `evidence_path` ขึ้นต้นด้วยโฟลเดอร์ของผู้เรียกเอง
3. ถ้ากิจกรรมบังคับรหัส: รหัสต้องตรงกับคู่ (student, activity), ยังไม่หมดอายุ, ยังไม่ถูกใช้หรือ revoke, และ `attempts` < 5
4. **ข้อควรระวังสำคัญ:** ถ้ารหัสผิดแล้วฟังก์ชัน `RAISE EXCEPTION` การนับ `attempts` ที่เพิ่มไปจะถูก rollback ไปด้วยและการล็อกรหัสไม่ทำงาน ฟังก์ชันจึงต้อง **คืนผลลัพธ์แบบมีรหัสข้อผิดพลาด** (`ok`, `error_code`) สำหรับกรณีรหัสผิด/หมดอายุ/ถูกล็อก แทนการ raise เพื่อให้การเพิ่ม `attempts` ถูก commit
5. ผ่านทุกเงื่อนไข: บันทึกการใช้รหัส (`used_at`), สร้าง submission `pending` + items, แจ้งเตือนครู/admin

## 8. สิทธิ์และความปลอดภัย

### 8.1 Row Level Security
ฟังก์ชันช่วย `is_staff()` (ครูหรือ admin) และ `is_admin()` ใช้ในนโยบายทุกตาราง

| ตาราง | นักเรียน | ครู | admin |
|---|---|---|---|
| `profiles` | อ่านของตัวเอง แก้ได้เฉพาะ `full_name`, `display_name` | อ่านทุกคน | อ่านทุกคน เปลี่ยน role ผ่านฟังก์ชันเท่านั้น |
| `activities` | อ่านเฉพาะที่เปิดอยู่และที่ตนเข้าร่วม | สร้าง/แก้/ลบ (ห้ามลบกิจกรรมที่มีผลแล้ว; ครูลบได้ตามการตัดสินใจของผู้ใช้ 2026-10-18) | สร้าง/แก้/ลบ (ห้ามลบกิจกรรมที่มีผลแล้ว) |
| `rewards`, `articles` | อ่านเฉพาะที่เปิดเผยแล้ว | สร้าง/แก้ | สร้าง/แก้/ลบ |
| `waste_categories` | อ่าน | อ่าน | แก้ได้ |
| `cart_items` | จัดการของตัวเองเท่านั้น | อ่านทั้งหมด | อ่านทั้งหมด |
| `participations`, `weigh_codes`, `submissions`, `submission_items`, `orders`, `order_items`, `ledger_entries` | อ่านของตัวเอง **เขียนตรงไม่ได้** | อ่านทั้งหมด **เขียนตรงไม่ได้** | อ่านทั้งหมด **เขียนตรงไม่ได้** |
| `notifications` | อ่านและทำเครื่องหมายว่าอ่านแล้วของตัวเอง | เหมือนกัน | เหมือนกัน |

ตารางที่เขียนตรงไม่ได้ เปลี่ยนผ่านฟังก์ชันในหัวข้อ 7 เท่านั้น (รวม `participations` ผ่าน `join_activity` เพื่อบังคับกฎเวลา)

### 8.2 กันผู้ใช้ยกระดับสิทธิ์
- RLS ของ `profiles` อนุญาตแก้เฉพาะบางคอลัมน์ และมี trigger ปฏิเสธการเปลี่ยน `role`/`is_demo` ที่ไม่ได้มาจากฟังก์ชัน admin
- `set_user_role` ห้ามลดระดับ admin คนสุดท้าย

### 8.3 บัญชีสาธิต
- บัญชี admin สาธิต (`is_demo` = true) **ห้าม** เปลี่ยนบทบาทหรือลบ admin จริง
- ข้อมูลและบัญชีสาธิตแยกจาก admin จริง รหัสผ่านบัญชีสาธิตต้องเปลี่ยนทันทีหลังวันนำเสนอ
- ยอมรับความเสี่ยงที่ใครมีสไลด์ก็เข้าบัญชีสาธิตได้ในช่วงสาธิต เพราะข้อมูลรีเซ็ตได้

### 8.4 รูปหลักฐาน
- Bucket แบบ private เส้นทาง `{student_id}/{submission_id}/...` นักเรียนอัปโหลดได้เฉพาะโฟลเดอร์ตัวเอง เจ้าของและ staff ดูผ่าน signed URL อายุสั้น
- จำกัดชนิด (jpeg/png/webp) และขนาดไม่เกิน 2 MB ย่อรูปบนไคลเอนต์ก่อนอัปโหลด (เป้าหมายราว 300 KB ต่อรูป)
- งานล้างรูปค้าง (ไม่มี submission ผูกเกิน 24 ชั่วโมง) รันวันละครั้งผ่าน Vercel Cron เรียก Route Handler ที่ใช้ `service_role` ลบผ่าน Storage API (ไม่ลบผ่าน SQL ตรง) ต้องตรวจเงื่อนไข cron ของแพ็กเกจ Vercel ที่ใช้ตอนทำ

### 8.5 กุญแจและการยืนยันตัวตน
- `service_role` key เก็บในตัวแปรสภาพแวดล้อมฝั่งเซิร์ฟเวอร์ของ Vercel เท่านั้น ห้ามเข้า git หรือเบราว์เซอร์
- ใบเสร็จ PDF และรายงานตรวจสิทธิ์ผู้ขอก่อนสร้าง (ออเดอร์เป็นของผู้ขอหรือผู้ขอเป็น staff, รายงานเฉพาะ staff)

### 8.6 อีเมล (สมัครและลืมรหัสผ่าน)
- อีเมลในตัวของ Supabase ใช้ทดสอบเท่านั้น (จำกัดต่ำมากและอาจส่งได้เฉพาะสมาชิกทีมโปรเจกต์) ต้องเปิด **custom SMTP** ซึ่งค่าเริ่มต้นหลังเปิดอยู่ที่ราว 30 อีเมลต่อชั่วโมงและปรับเพิ่มได้
- ต้องปรับขีดจำกัดอีเมลต่อชั่วโมงให้พอกับจำนวนคนที่คาดว่าจะสมัครพร้อมกันในวันสาธิต
- ต้องเลือกผู้ให้บริการและที่อยู่ผู้ส่งในเฟส 0 (ดูหัวข้อ 14)
- **แผนสำรอง:** ปิดการยืนยันอีเมลช่วงสาธิตด้วยการตั้งค่า ไม่ต้องแก้โค้ด

### 8.7 ข้อจำกัดแพ็กเกจฟรีของ Supabase (ตรวจเมื่อ ต.ค. 2026 ให้ตรวจซ้ำก่อนวันสาธิต)
- ฐานข้อมูล 500 MB, พื้นที่ไฟล์ 1 GB, โปรเจกต์ฟรีถูกพักหลังไม่มีการใช้งานหนึ่งสัปดาห์ (ต้องกดเปิดใหม่เอง)
- การรับมือ: ย่อรูป, เข้าใช้งานโปรเจกต์ทุกสัปดาห์ช่วงพัฒนา, เปิดเว็บก่อนวันสาธิต 1-2 วัน (ถ้าโปรเจกต์ถูกพัก งาน pg_cron ยกเลิกออเดอร์ก็หยุดด้วย)

### 9.4 หน้าจอสำคัญ
- **ฟอร์มส่งผล:** ช่อง kg และขีดแยกตามกลุ่ม (แปลงเป็นกรัมเอง) ปุ่มถ่ายรูปเปิดกล้องมือถือโดยตรง ช่องรหัสยืนยัน (เฉพาะกิจกรรมที่บังคับ) และกล่อง "ประมาณการแต้มและ carbon" พร้อมข้อความว่าแต้มจริงได้เมื่อครูตรวจผ่าน
- **หน้าตรวจผล:** รูปหลักฐานข้างตัวเลขที่นักเรียนกรอก ธงเตือนน้ำหนักสูงผิดปกติ (และรูปซ้ำ ถ้าทำฟีเจอร์เสริม) ปุ่มอนุมัติ/ปฏิเสธ (ปฏิเสธต้องกรอกเหตุผล)

### 9.5 แจ้งเตือน
ไอคอนกระดิ่งแสดงจำนวนยังไม่อ่านและอัปเดตทันทีด้วย Realtime (ตามสิทธิ์ RLS ของผู้ใช้) เหตุการณ์ที่สร้างแจ้งเตือน:
ส่งผลใหม่ (ถึงครู/admin), ผลถูกอนุมัติ/ปฏิเสธ, แลกของสำเร็จ, ของพร้อมรับ/รับแล้ว, ออเดอร์ถูกยกเลิก/หมดอายุ, กิจกรรมใหม่เปิดรับ (ถึงนักเรียนทุกคน)

## 10. รายงาน

ทุกรายงานเลือกช่วงวันที่ได้ ใช้เขตเวลา Asia/Bangkok และนับเฉพาะ **ผลที่อนุมัติแล้ว ของกิจกรรมที่จบแล้ว** (สถานะ `closed` หรือพ้น `ends_at`) ผลที่ยังรอตรวจ ถูกปฏิเสธ หรือเป็นของกิจกรรมที่ยังไม่จบ จะไม่ถูกนับ

**เกณฑ์วันที่ (ผู้ใช้ยืนยันแล้ว):** ช่วงวันที่ที่เลือกกรองตาม **วันที่จบกิจกรรม (`ends_at`)** ผลที่อนุมัติหลังกิจกรรมจบยังนับรวมในช่วงของกิจกรรมนั้น ดังนั้นตัวเลขของช่วงที่ผ่านไปแล้วอาจเพิ่มขึ้นได้ถ้ามีผลที่อนุมัติทีหลัง

**ข้อควรรู้:** dashboard และอันดับคำนวณจาก ledger ซึ่งนับทันทีที่อนุมัติ (แต้มเข้าบัญชีทันที) ตัวเลขจึงอาจสูงกว่ารายงานชั่วคราวระหว่างที่กิจกรรมยังไม่จบ หน้ารายงานต้องมีหมายเหตุบอกเกณฑ์นี้

### 10.1 CSV
- เข้ารหัส UTF-8 แบบมี BOM เพื่อให้ Excel เปิดแล้วภาษาไทยไม่เพี้ยน
- สองไฟล์ (ผู้ใช้ยืนยันคอลัมน์แล้ว): **รายกิจกรรม** (กิจกรรม วันที่ จำนวนผู้เข้าร่วม จำนวนผลที่อนุมัติ น้ำหนักแยก 4 กลุ่ม จำนวนต้นไม้ แต้มที่ให้ carbon) และ **รายนักเรียน** (ชื่อ แต้มที่ได้ carbon น้ำหนักรวม จำนวนต้นไม้ ในช่วงที่เลือก)

### 10.2 PDF สรุป
- ตัวเลขรวมของช่วงที่เลือก และกราฟ 3 ตัว: **carbon ที่ลดได้**, **น้ำหนักขยะที่เก็บ (แยก 4 กลุ่ม)**, **จำนวนต้นไม้ที่ปลูก**
- ฝังฟอนต์ไทยในไฟล์ กราฟวาดจากข้อมูลชุดเดียวกับ dashboard เป็นรูปแบบเวกเตอร์ที่ไลบรารีสร้าง PDF วาดเองได้ ไม่พึ่งเบราว์เซอร์เสมือนบน Vercel
- ไลบรารีที่ใช้เลือกในขั้นแผนพัฒนา โดยต้องผ่านการทดสอบการแสดงผลภาษาไทย (สระและวรรณยุกต์ซ้อนกันถูกต้อง) ก่อนเลือกใช้ ใช้ไลบรารีเดียวกันกับใบเสร็จ PDF

### 10.3 ใบเสร็จออเดอร์ (PDF)
เลขออเดอร์ วันที่ ชื่อผู้แลก รายการ จำนวน แต้มต่อชิ้นและรวม สถานะ วันหมดอายุการรับของ สร้างตามคำขอจากหน้าออเดอร์ ใช้ได้ทั้งออเดอร์ที่รอรับและรับแล้ว

## 11. การทดสอบ

- **ฟังก์ชันฐานข้อมูล (pgTAP):** ใช้รหัสซ้ำไม่ได้, รหัสหมดอายุ, รหัสผิด 5 ครั้งแล้วล็อกจริง (ยืนยันว่า `attempts` ถูก commit), อนุมัติซ้ำไม่ได้แต้มซ้ำ, ผู้ตรวจเป็นเจ้าของผลไม่ได้, กดแลกพร้อมกันสองเครื่องแล้วแต้มไม่ติดลบและสต็อกไม่เกิน, ออเดอร์หมดอายุแล้วคืนแต้มและสต็อกครบ, ปัดเศษแต้มตามสูตร 6.1
- **สิทธิ์ (RLS):** ล็อกอินเป็นนักเรียนแล้วแก้ role ตัวเองไม่ได้, เขียน ledger ตรงไม่ได้, อ่านผลหรือรูปของคนอื่นไม่ได้, บัญชีสาธิต admin เปลี่ยน admin จริงไม่ได้
- **ฝั่งแอป:** Vitest สำหรับฟังก์ชันคำนวณล้วน (แปลง kg/ขีดเป็นกรัม, ประมาณการแต้ม) และ Playwright เส้นทางหลัก: สมัคร → เข้าร่วม → ส่งผล → ครูอนุมัติ → แลกของ → ยืนยันรับของ
- **มือถือจริง:** ทดสอบตามเช็กลิสต์ก่อนวันสาธิต (สแกน QR, ถ่ายรูป, อัปโหลด, อ่านง่าย)
- **สภาพแวดล้อม:** Supabase local ผ่าน Docker ถ้ารันได้ ถ้าไม่ได้ใช้โปรเจกต์ Supabase ฟรีตัวที่สองเป็นโปรเจกต์ทดสอบ

## 13. ข้อมูลตัวอย่างและวันสาธิต

### 13.1 ข้อมูลตัวอย่าง (seed)
สคริปต์เดียวที่รันซ้ำได้ ใส่: นักเรียนจำลองราว 30 คน (ชื่อสมมติ ไม่ใช้ชื่อคนจริง), กิจกรรมราว 6 รายการ (ผสมสามชนิด มีทั้งที่จบแล้วและที่กำลังเปิด), ผลที่อนุมัติแล้วกระจายในช่วง 3 เดือนที่ผ่านมา, ของรางวัลราว 8 ชิ้น, ออเดอร์ตัวอย่างบางส่วน และบทความตัวอย่าง
ค่า carbon ต่อ kg ใน seed ใช้ค่าอ้างอิงจริงตามหัวข้อ 6.2 เท่านั้น

### 13.2 บัญชีสาธิต
3 บัญชี (นักเรียน ครู admin) ที่ติดแฟลก `is_demo` และสร้างให้ยืนยันอีเมลแล้ว มีสคริปต์ 2 โหมด: **รีเซ็ตข้อมูลสาธิต** (รันซ้ำ seed) และ **ล้างข้อมูลผู้ใช้ทั้งหมดที่ไม่ใช่ admin จริง** ก่อนวันนำเสนอ

### 13.3 เช็กลิสต์และสคริปต์นำเสนอ
- **ก่อนวัน 1-2 วัน:** เปิดเว็บเพื่อกันโปรเจกต์ถูกพัก, ทดสอบอีเมลสมัครและลืมรหัสผ่านด้วยบัญชีภายนอก, รัน seed รีเซ็ต, ทดสอบสแกน QR จากมือถือหลายเครื่อง
- **สคริปต์ 8-10 นาที:** หน้าแรกและ dashboard ที่มีข้อมูล → ครูสร้างกิจกรรมสด → ผู้ชมสแกน QR สมัครและเข้าร่วม → ออกรหัสที่จุดชั่งจำลอง → ส่งผล → ครูอนุมัติเห็นแจ้งเตือนเด้ง → แลกของและดาวน์โหลดใบเสร็จ → อันดับและรายงาน PDF
- **แผนสำรอง:** วิดีโอ flow หลักที่อัดไว้, ฮอตสปอตมือถือสำรอง, วิธีรันแบบ local ในเอกสาร
- **หลังวันสาธิต:** เปลี่ยนรหัสผ่านบัญชีสาธิตทันที

## 14. ความเสี่ยงและประเด็นที่ต้องตัดสินใจในขั้นถัดไป

| ความเสี่ยง/ประเด็น | การรับมือ |
|---|---|
| อีเมลหรือ SMTP ตั้งค่าผิดวันสาธิต | ทดสอบก่อนวัน, ปรับขีดจำกัดต่อชั่วโมง, สลับเป็นปิดการยืนยันอีเมลได้ |
| โปรเจกต์ Supabase ถูกพัก | เปิดใช้งานทุกสัปดาห์ และก่อนวันสาธิต 1-2 วัน |
| ช่องโหว่การกดพร้อมกันในฟังก์ชัน SQL | ล็อกแถว + เทสต์การแข่งกันโดยเฉพาะ |
| ภาษาไทยใน PDF แสดงผลผิด | ทดสอบไลบรารีและฟอนต์ตั้งแต่เฟส 2 ก่อนทำรายงานในเฟส 3 |
| ขอบเขตบานปลาย | ล็อกฟีเจอร์กลาง ก.พ. ตัดฟีเจอร์เสริมก่อน |
| **ต้องเลือกในเฟส 0:** ผู้ให้บริการอีเมล SMTP และที่อยู่ผู้ส่ง (บางผู้ให้บริการต้องยืนยันโดเมนหรืออีเมลผู้ส่ง ซึ่งวิทยาลัยอาจไม่มีโดเมนของตัวเอง) | ตรวจเงื่อนไขล่าสุดของผู้ให้บริการที่แพ็กเกจฟรีรองรับ ณ ตอนนั้น |
| **ต้องหาในเฟส 0-1:** ค่าอ้างอิง carbon ของ 4 กลุ่มขยะและต้นไม้ พร้อมที่มา | ค้นแหล่งที่ตรวจสอบได้ (เช่น อบก.) ถ้าไม่ครบแจ้งเจ้าของโปรเจกต์ |
| **ต้องเลือกในเฟส 2:** ไลบรารีสร้าง PDF ที่ฝังฟอนต์ไทยได้ถูกต้อง | spike ทดสอบแสดงผลก่อนเลือก |

## 15. สมมติฐานที่ใช้ใน spec นี้ (ผู้ใช้ยืนยันแล้วในส่วนที่ 3-5)

- ช่วงส่งผลคือ `starts_at` ถึง 3 วันหลัง `ends_at`
- ส่งผลที่ถูกปฏิเสธใหม่ต้องใช้รหัสใหม่ (เมื่อกิจกรรมบังคับรหัส)
- แจ้งเตือน "กิจกรรมใหม่" ส่งถึงนักเรียนทุกคน
- ครูจัดการกิจกรรม ของรางวัล และบทความได้ ส่วนเปลี่ยนบทบาทและแก้อัตราคะแนนเป็นของ admin
- ภาษาไทยอย่างเดียว

**สมมติฐานที่ผู้ใช้ยืนยันแล้ว (14 ต.ค. 2026):**
- สูตรปัดเศษแต้มตามหัวข้อ 6.1 (ปัดลงเป็นจำนวนเต็มต่อหนึ่งผลที่ส่ง)
- แหล่งอ้างอิง carbon หลักคือ อบก. (หัวข้อ 6.2)
- รายงานนับเฉพาะผลที่อนุมัติแล้วของกิจกรรมที่จบแล้ว (หัวข้อ 10)
- รายงาน CSV สองไฟล์ตามคอลัมน์ในหัวข้อ 10.1 และ PDF ฟอนต์ไทยพร้อมกราฟ 3 ตัวตามหัวข้อ 10.2
- ปริมาณ seed: นักเรียนราว 30 คน กิจกรรมราว 6 รายการ ของรางวัลราว 8 ชิ้น (ปรับได้ภายหลัง)
- อันดับรายเดือนใช้เดือนปฏิทินตามเขตเวลา Asia/Bangkok
- รายงานกรองช่วงวันที่ตาม `ends_at` ของกิจกรรม (หัวข้อ 10)
